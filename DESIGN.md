## Typography

- Body: Inter
- Headings: Fraunces (a serif with some personality, used sparingly for `h1`–`h3`)

Both fonts are loaded once, from Google Fonts, and shared across themes — only the color tokens change between professional and personal.

## Layout system

- `_layouts/professional.html` and `_layouts/personal.html` share `_includes/head.html` and `_includes/footer.html`, and only differ in body class and nav include. This is the only place theme markup should be duplicated — everything else should be a shared include.
- `_layouts/home.html` is now a bright, playful, button-free hero — not the neutral dark split it started as, and not a landing page with CTAs either. See "The homepage has no buttons" below.
- Content pages are Markdown with front matter (`layout: professional` / `layout: personal` / `layout: home`), not raw HTML, so adding a new page never means re-writing `<head>` or nav.

## Shared cross-side buttons

Two button components live in `tokens.css` (not a theme file) because they appear on every page, always with the same fixed colors regardless of which page's background they sit on — the button's own identity signals which side it leads to, the way a "professional" and "personal" doorway might look different from either side of the wall.

- **`.offset-btn`** — "the professional button." Ghost-style pill: `background: var(--bg)` and `border`/`text: var(--text)`, so it's white/black-dashed on light pages and dark/white-dashed on the personal page, matching whatever theme it's placed on. Blue (`#1d4ed8`) is the one constant — it only shows up in the hover shadow, same color on every page. Shape never changes, only position/shadow animate on hover. Padding/font-size use `clamp()` so it scales smoothly rather than jumping between fixed sizes; `.site-header .offset-btn` still sets a smaller ceiling for the nav context. Used for: the homepage's primary CTA, the résumé's Email/LinkedIn actions, and the header nav link into `/resume/` (on the personal page).
- **`.keycap-btn`** — "the personal button." A rectangular key (8px radius, not a pill) with a solid offset "lip" standing in for its side wall — the classic flat-3D keycap trick, no perspective/rotation (an earlier tilted isometric version was hard to read). Hover only adds a glow, never moves; `:active` collapses the lip and drops the key down 4px, like an actual keypress. Sized to match plain nav-link text (0.95rem) rather than standing out next to "Resume"/"Life & Instagram". `#12181f` fill, `#6ec1ff` glow, from the personal theme's palette. Used for: the homepage's secondary CTA and the header nav link into `/life/` (on the professional page).
- **One button per cross-side link, no duplicates:** each page has exactly one path to the other side — the header nav link, styled as the button matching the *destination's* theme. Don't also add a same-purpose button in the page body; that was tried and reverted (see CLAUDE.md tooling log) because two ways to do the same thing on one page reads as redundant, not extra-helpful.
- **Watch for this bug:** both themes set a blanket `a { color: var(--accent) }` for prose links, which has higher specificity (class+type) than a bare `.offset-btn`/`.keycap-btn` class rule — without `!important` on the button's own `color`, its label renders in accent-on-accent (or theme-on-theme) and disappears. Already fixed in `tokens.css`; keep it in mind if either theme's link-color rule changes.
- **Naming:** avoid both the literal "Professional"/"Personal" wording and pure-engineer jargon (two earlier passes tried "Enter Production"/"peek at Localhost" and then "See the Résumé"/"Off the Clock" — the first was engineer-only jargon, the second still said "résumé" out loud, which the user explicitly didn't want). Current names — **The Grind** (professional) and **The Chaos** (personal) — echo the homepage's own established voice ("skip straight to the chaos") instead of describing the destination literally. Same name everywhere that destination appears: the page's own nav self-link, and the cross-link button on the other side.

## Résumé hero: Text Fall

The `/resume/` `<h1>` name is a canvas particle effect (`assets/js/text-fall.js`), ported from a React/canvas component the user supplied ("Text Fall"). Same accessibility pattern as spotlight-text: `.text-fall-plain` (the real "Bhavesh Nakum" text) is what's actually in the DOM and stays visible by default; the script adds `.text-fall-ready` to the heading only once it's confirmed set up, and only then does CSS swap to the canvas and visually clip the plain text off-screen (never `display:none`, so it's still the `h1`'s accessible name). No JS, a script error, or `prefers-reduced-motion` all just leave the plain heading showing.

- **It's a texture, not literal text.** Particles are sampled from an alpha mask of the rendered name (`buildTextMask`/`sampleTargets`), so their *positions* trace the name's shape — but each particle's glyph is a random monospace character (`randChar()`), re-rolled continuously via `maybeScramble`. No code path ever paints a particle with its "correct" letter. This matches the original component's aesthetic (a "digital noise" title, not a dot-matrix font) — the readable name lives in `.text-fall-plain`, the canvas is decorative.
- **Density is tuned via `glyphSize`.** The example config pasted by the user (`glyphSize: 15`) produced only ~31 particles for a 13-character name — visually a sparse scatter, unrecognizable as any shape. Dropped to `glyphSize: 7`, giving several hundred sample points against the same mask — a legible dot-matrix-style density without hitting the 4200-particle cap (`MAX_PARTICLES` in `text-fall.js`). If the name ever changes, re-check this: fewer/longer characters need a different `glyphSize` to stay legible.
- **Interaction:** click toggles idle particles into a "fall" (gravity + bounce), then "form" back into place; a second click "spreads" them out again. Cursor proximity applies a magnetic pull (`applyMagnetic`) while hovering. `autoFall: true` + an `IntersectionObserver` also triggers the fall once the heading scrolls into view (≥80% visible), so the very first page load isn't a static scatter forever.
- **Deliberate cut from the original component:** the entire SVG-logo fallback mode (`LOGO_SVG_DESKTOP`/`MOBILE`, `svgToImage`, the logo branch in `ensureMask`) was dropped — this site always passes real text (`text: "BHAVESH NAKUM"`), so that whole code path would never execute. Also dropped: TypeScript types, and Framer's `RenderTarget`/static-export handling (this is a plain script tag, not a React/Framer runtime).
- **A real automation-only false alarm worth remembering:** the canvas rendered completely blank (0 particles) the first time this was tested against a local server, tracing to `dispScale` computing near-zero. Root cause was the *testing tool's* browser tab reporting a 0×0 viewport (`.text-fall-root.offsetWidth === 0`) because the pane was backgrounded — not a bug in `resizeCanvas()`/`updateBounds()`. A real visitor's tab always has real dimensions from first paint. `text-fall.js` already has a `ResizeObserver` on the root element that would self-correct if this ever happened for real (e.g. a tab restored from background with genuinely stale layout).

## Homepage background: Beyond Horizon, and a color-theory pass

After several rounds of independently-added hero decorations (pastel blobs, a multi-hue glitter canvas, a blue galaxy button, italic spotlight text, a page-corner/orb hint), the user flagged the accumulated result as not blending together — a real UX problem, not a nitpick: each addition had picked its own colors in isolation instead of drawing from one shared palette. The fix was a WebGL ambient background (`assets/js/beyond-horizon.js`, ported from a React/WebGL "sunrise over a planet edge" component the user supplied) plus retinting everything else to match it, rather than adding yet another independently-colored layer.

- **What it is:** a full-bleed canvas (`.hero-glow`/`.hero-glow-canvas`, behind everything else in `.hero`) rendering a glowing horizon — a bright core sitting on the edge of a huge dark disc, with volumetric violet/indigo haze rising off it, on a near-black background. Cursor movement subtly parallaxes the glow (eased, not snapped); hovering the hero saturates the core and widens the rim. Ported faithfully: the GLSL is written from scratch (the reference's own comments note its source engine's compiled shader carries a commercial license, so nothing from it is transcribed — only the *composition*, which is a description of what's visible, plus constants the original author measured off a reference capture, e.g. `HORIZON_Y = 0.7055` from the brightest measured pixel). React scaffolding (props/refs/useEffect) is dropped for one hardcoded `CONFIG` object and plain DOM APIs, matching every other canvas effect on this page — this runs exactly once, so a reusable component API would be unused abstraction.
- **The `fit` dial is what makes it responsive, not a media query.** Every measured constant is in units of the element's *width*, which is exactly right at the reference's aspect ratio and wrong at any other: hold the width and grow the height (a phone in portrait) and a naively-ported version keeps the glow's absolute size while the empty space around it grows, leaving a small dot lost in a big black field — confirmed exactly this way in an early check before `fit` was wired in. `unit = (aspect / REF_ASPECT) ^ fit` rescales every position by that factor; `fit: 0.5` (shipped) is the geometric mean between width-locked (`0`) and height-locked (`1`), because the two demands genuinely pull opposite ways — glow *size* wants to track height, horizon *curvature* wants to track width (a planet edge crossing a narrow phone frame really is nearly straight, so the arc flattening out on mobile is correct, not a bug). Verified at 375×812, 768×1024, and desktop — the glow sits behind the "Explore" button at every width instead of drifting into empty space.
- **This is now the single color source for the whole homepage**, not just a background. `.theme-home`'s tokens flipped from a white/dark-text page (`--bg:#ffffff`, `--text:#14171c`) to match the shader's own near-black/white/lavender palette (`--bg:#08080a`, `--text:#f3f1f7`, new `--accent:#b79bfa`, matching `MID_COLOR` in the shader). Lavender/indigo (~hue 260) sits *analogous* to the site's existing blues (Grind `#1d4ed8` ~hue 225, Chaos `#6ec1ff` ~hue 205) rather than clashing with them — those didn't need to change, and are kept deliberately as a secondary "this hints at a themed destination" signal (see page-corner/portal-orb below). The actual clashing colors were the blob/glitter blues-plus-amber-plus-green, which had no relationship to anything else on the page; removing them, not just adding a fourth palette on top, is what actually fixed "doesn't blend in."
- **Deprecated, not deleted: `.hero-blobs` and `.hero-glitter`.** Both are superseded by `.hero-glow` and disabled via one `display: none` rule each in `home.css`, markup and JS files fully intact. `glitter.js` additionally isn't loaded by `home.html` anymore (its `<script>` tag is commented out, file untouched) — a hidden `<canvas>` still running its own `requestAnimationFrame` draw loop forever would burn CPU/battery for zero visible effect, which a CSS-only animation (like the still-`display:none`'d `.hero-stars` before it) doesn't cost. Re-enabling either needs at most one CSS rule removed and one script tag restored.
- **Contrast-only fixes** (not color-theory decisions, just "this assumed a light background and would vanish on a dark one"): `.portal-orb` was a dark dot on a light page, flipped to a light dot (still same blue glow) so it reads as a star against the new near-black backdrop; `.portal-orb-label`'s dark chip on a light page became a light-bordered dark chip so it doesn't merge into the equally-dark page behind it; `.spotlight-text`'s "nearly invisible dim state" trick (`rgba(20,23,28,0.08)`, near-black-on-white) inverted to near-white-on-black; `.page-corner-back`'s underside color (`#0f1419`) was deepened to indigo (`#1c1430`) since it had become nearly indistinguishable from the new `#08080a` page background, which would have made "peel the corner back on hover" reveal nothing.
- **`.hero-dim` inverted into `.hero-hover-glow`.** This was a dark radial gradient meant to dim a *light* page when hovering the galaxy button — a scoped stand-in for the reference galaxy-button's whole-page black-out. Once the homepage background became near-black itself, darkening it further was imperceptible, so the effect flipped into a lavender *bloom* instead: hovering "Explore" now reads as the button lighting up its own patch of the same night sky the WebGL background renders, rather than fighting it. Same mechanism (`:has()`-driven opacity fade), inverted color and renamed for what it now actually does.
- **`.galaxy-button`'s `--hue` moved from 205 (personal-theme blue) to 262** (the Beyond Horizon lavender, `#B79BFA`) once that became the page's own background color — still blue-violet analogous, just matched to what's now directly behind the button instead of to the destination page's theme.

## The homepage: mostly no buttons, plus one deliberate exception

`.offset-btn`/`.keycap-btn` (the shared cross-side components) never appear on the hero — the idea is a homepage people poke around in rather than one that funnels them through a corporate CTA, per explicit direction: "home page should be interactive and center of attraction... people should spend more time on home page to explore." The one exception is `.galaxy-button` (below), added later as a deliberately overt "Explore" CTA alongside the subtle hints — the mix of "some things you have to notice, one thing that's obvious" is intentional, not a walk-back of the original direction.

- **Backgrounds, in order of who's currently active:** `.hero-glow` (Beyond Horizon, the WebGL glow — current default) → `.hero-glitter` (canvas warp-tunnel, DEPRECATED) → `.hero-stars` (CSS twinkling dots, DEPRECATED, superseded by `.hero-glitter` before it was itself superseded) → `.hero-blobs` (cursor-reactive pastel blobs via `hero.js`'s `--mx`/`--my`, DEPRECATED). All three deprecated layers are fully intact and re-enablable; see "Homepage background: Beyond Horizon" above for what superseded them and why only one should ever run at once.
- **The Chaos is a page corner on desktop, a portal orb on mobile — never both at once.** `.page-corner` (top-right) reads as this page's own corner lifting slightly, like paper in a breeze — a dark triangle (`.page-corner-back`) under a white one (`.page-corner-front`) that flutters via `@keyframes` and peels back further on hover/focus. `.portal-orb` is the earlier floating-dot version, kept only for narrow viewports (`display:none` by default, shown at `max-width:640px`; `.page-corner` does the reverse) — the user didn't like the orb on desktop but wanted it back for mobile, where the corner-peel is fiddlier to notice/tap. Both are real `<a href="/life/">` links (the corner via `aria-label`, since its shapes carry no text). Clicking either navigates with the sitewide wipe transition; a fuller "the page tears away, particles drift left, black background" effect was explicitly asked for but deferred as its own later phase — that needs canvas, not CSS, to do properly.
- **Galaxy button ("Explore"):** an overt CTA into `/life/`, sitting in `.hero-inner` below the subhead — unlike everything else on this list, not disguised as scenery. A structural port of a CodePen "galaxy button" the user supplied (HTML/CSS/JS, no framework attached) — the first pass simplified it into a much flatter effect (flat 2D star ring, single-layer spark, always-visible static stars) that the user correctly flagged as not matching the reference; this version ports the actual mechanics: a single `--active` custom property (0 at rest, 1 on hover/focus) that every child reads via `var()` — the dual radial-gradient background, the glow/inset box-shadow, the spark rim, and the star ring all wake up together, same as the original. The star ring is genuinely 3D (`.galaxy__ring` tilted via `rotateX`/`rotateY` inside a `perspective`d parent), not a flat circle — that tilt is the effect's visual signature. The "spark" rim is the original's two-layer trick: a masked wrapper that flips between top/bottom half on a stepped timer, with a continuously-spinning conic-gradient pseudo-element underneath. Per-star orbit distance/size/alpha/duration/delay come from `assets/js/galaxy-button.js`, a near-verbatim port of the reference's own randomizing script (`querySelectorAll('.star')` + inline custom properties) — replacing the flat-ring version's `--i`-based CSS-only placement. `--hue` (now 262, see above — originally 205) sets the accent throughout. Static-star drift distance and the galaxy disc's size are scaled down from the reference's values, which were sized for a much bigger standalone demo button. The reference also dims the *entire page* on hover via `body:has(button:hover)`, which was skipped in the first redo pass as wrong for a page with its own glitter/blob background; a scoped follow-up (`.hero-hover-glow`, see above — originally `.hero-dim`, a dark version) ports the same idea at hero scale instead, faded in via `.hero:has(.galaxy-button:hover, .galaxy-button:focus-visible)`. Progressive enhancement: browsers without `:has()` just don't get it, the button itself is unaffected. All animations (`.star`, `.star--static`, `.spark`, `.spark::before`) drop out under `prefers-reduced-motion`, leaving a plain static pill.
- **The Grind still starts with a scroll**, but the "keep going" scroll-cue is now a real `<a href="/resume/">`, not just a hint — this had to change from the original plain-div version, because `prefers-reduced-motion` skips the entire scroll-driven mechanic below, and with no CTA button left on the page, reduced-motion/no-JS/keyboard users would otherwise have had zero path to `/resume/` from the homepage. Never rely on a single JS-only mechanic being the sole path to a page.
- **Spotlight text — a second, quieter hint at `/life/`:** `.spotlight-text` ("I left the interesting parts out of the résumé.", italic Fraunces) sits top-right (bottom-right on narrow screens), a recreation of the Cred "flashlight" effect — a dim base layer and a pixel-aligned bright duplicate on top, the bright one masked by a `radial-gradient` that follows the cursor (`--spot-x`/`--spot-y`, `mask-image`), so hovering sweeps a small circle of full brightness across the text. Same accessibility principle as the portal orb, taken further: the **enhancement itself is feature-detected**, not just reduced-motion-gated — `hero.js` only dims the text and wires up the cursor tracking (adding `.spotlight-ready`) when `matchMedia('(hover: hover)')` actually matches, i.e. a real mouse. Touch devices, reduced-motion, and no-JS all just get the plain `var(--muted)`-colored link, fully readable, never truly hidden. `--spot-size` (the reveal radius) is a `@property`-registered custom property so it can transition smoothly on hover/focus-visible; `--spot-x`/`--spot-y` update instantly via `pointermove`, no transition, so the spotlight tracks the cursor without lag. Two separate hints at `/life/` (this + the portal orb) is intentional, not redundant — an exploratory homepage rewards finding more than one thing.
  - **The two layers must share `font: inherit`, not just matching colors.** They're the same text rendered twice and have to line-break identically, or the mask reveals bright glyphs sitting somewhere the dim glyphs underneath aren't — this actually happened: an early version bolded only the bright layer, which widened its glyphs enough to wrap differently at some (but not all) viewport widths, so it looked fine on mobile and visibly double-exposed on desktop. Any future style tweak to one layer needs the identical tweak on the other, or use `font: inherit`/shared properties on the parent so both pick it up automatically.
- **A console-only easter egg, homepage only:** a styled `console.log` (`hero.js`) pointing curious devs at the GitHub source — visible via the browser's DevTools console (Cmd+Option+J in Chrome), not on the page itself. A Konami-code keyboard listener was tried and removed: it worked, but had zero real discovery rate without an on-page hint, and a hint defeats the point of a hidden code. Lesson: an easter egg needs *some* plausible discovery path (a known convention like "check the console," a visible hint, or both) — "technically present but unfindable" isn't a feature, it's just more code to maintain.

## Scroll-to-enter and page transitions (`v3-transition`, complete)

- **Scroll-to-enter, not scroll-jacking:** an `IntersectionObserver` on a sentinel past a `.scroll-runway` spacer (`assets/js/hero.js`) navigates to `/resume/` once the user has actually scrolled and reached the bottom. Native scroll is never intercepted or altered mid-scroll. Skipped entirely under `prefers-reduced-motion` — the "keep going" link (see above) is the fallback path.
- **The scroll-veil builds the anticipation:** as the user scrolls through `.scroll-runway` toward the sentinel, `hero.js` computes progress (0–1) and writes it to `--scroll-progress` on `<html>`; a `position: fixed` radial blue glow (`.scroll-veil`) uses that as its `opacity`, intensifying well before the actual navigation fires. This is what makes the transition feel like it "starts" on scroll rather than snapping only at the very end.
- **The page transition itself is a wipe, not a cross-fade:** `@view-transition { navigation: auto; }` in `tokens.css` opts every page into the browser's native Cross-Document View Transitions API (pure CSS, no JS). `::view-transition-new(root)` animates in via `clip-path: inset()` (bottom-to-top reveal, echoing the scroll-down gesture) while `::view-transition-old(root)` just dims. This is what every navigation on the site gets by default, including arrival at `/life/`. Disabled under `prefers-reduced-motion`.
- **The one exception — a canvas "Thanos snap" on the jump into `/life/`:** `assets/js/dissolve.js` intercepts clicks on `.page-corner`/`.portal-orb` specifically (not every link into `/life/` — just these two deliberate hints), adds a `.dissolving` class that fades the hero to black, and drives a `<canvas>` of small (1–2.5px) squares blown apart to the left, then calls `location.href` once the animation finishes. Particles are sampled per real content element (`h1`, subhead, the galaxy button, spotlight-text, scroll-cue, the hint links themselves) rather than one uniform full-viewport grid, so each piece of the page reads as disintegrating on its own rather than a single generic overlay. Each particle's delay is a function of its own x-position (`(viewportWidth - x) / viewportWidth * 450ms`) so the dissolve visibly sweeps right-to-left across the screen instead of firing everywhere at once. This was explicitly deferred earlier ("which we will do once landing page is done") as its own later phase once the rest of the homepage felt settled. Because it's a real navigation (not `history.pushState`), the sitewide `@view-transition` wipe still runs on top once `location.href` fires — the canvas handles a dramatic *exit*, the shared wipe still handles every page's *entry*, so `/life/` doesn't look inconsistent with how every other page arrives. `prefers-reduced-motion` skips the whole script, same as everywhere else — the click falls through to the plain `<a href="/life/">` underneath.
