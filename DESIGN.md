## Typography

- Body: Inter
- Headings: Fraunces (a serif with some personality, used sparingly for `h1`–`h3`)

Both fonts are loaded once, from Google Fonts, and shared across themes — only the color tokens change between professional and personal.

## Layout system

- `_layouts/professional.html` and `_layouts/personal.html` share `_includes/head.html` and `_includes/footer.html`, and only differ in body class and nav include. This is the only place theme markup should be duplicated — everything else should be a shared include.
- `_layouts/home.html` is now a bright, playful, button-free hero — not the neutral dark split it started as, and not a landing page with CTAs either. See "The homepage has no buttons" below.
- Content pages are Markdown with front matter (`layout: professional` / `layout: personal` / `layout: home`), not raw HTML, so adding a new page never means re-writing `<head>` or nav.

## Shared cross-side buttons

Two button components live in `tokens.css` (not a theme file) because they appear on every page, always with the same fixed colors regardless of which page's background they sit on — the button's own identity signals which side it leads to, the way a "professional" and "personal" doorway might look different from either side of the wall.

- **`.offset-btn`** — "the professional button." Ghost-style pill: `background: var(--bg)` and `border`/`text: var(--text)`, so it's white/black-dashed on light pages and dark/white-dashed on the personal page, matching whatever theme it's placed on. Blue (`#1d4ed8`) is the one constant — it only shows up in the hover shadow, same color on every page. Shape never changes, only position/shadow animate on hover. Padding/font-size use `clamp()` so it scales smoothly rather than jumping between fixed sizes; `.site-header .offset-btn` still sets a smaller ceiling for the nav context. Used for: the homepage's primary CTA, the résumé's Email/LinkedIn actions, and the header nav link into `/resume/` (on the personal page).
- **`.keycap-btn`** — "the personal button." A rectangular key (8px radius, not a pill) with a solid offset "lip" standing in for its side wall — the classic flat-3D keycap trick, no perspective/rotation (an earlier tilted isometric version was hard to read). Hover only adds a glow, never moves; `:active` collapses the lip and drops the key down 4px, like an actual keypress. Sized to match plain nav-link text (0.95rem) rather than standing out next to "Resume"/"Life & Instagram". `#12181f` fill, `#6ec1ff` glow, from the personal theme's palette. No longer used on `/resume/`, where `.galaxy-button` (see "The homepage: mostly no buttons" below) replaced it in the nav per explicit request; still the component to reach for anywhere else that needs a plain "into `/life/`" link.
- **One button per cross-side link, no duplicates:** each page has exactly one path to the other side — the header nav link, styled as the button matching the *destination's* theme. Don't also add a same-purpose button in the page body; that was tried and reverted (see CLAUDE.md tooling log) because two ways to do the same thing on one page reads as redundant, not extra-helpful.
- **Watch for this bug:** both themes set a blanket `a { color: var(--accent) }` for prose links, which has higher specificity (class+type) than a bare `.offset-btn`/`.keycap-btn` class rule — without `!important` on the button's own `color`, its label renders in accent-on-accent (or theme-on-theme) and disappears. Already fixed in `tokens.css`; keep it in mind if either theme's link-color rule changes.
- **Naming:** avoid both the literal "Professional"/"Personal" wording and pure-engineer jargon (two earlier passes tried "Enter Production"/"peek at Localhost" and then "See the Résumé"/"Off the Clock" — the first was engineer-only jargon, the second still said "résumé" out loud, which the user explicitly didn't want). Current names — **The Grind** (professional) and **The Chaos** (personal) — echo the homepage's own established voice ("skip straight to the chaos") instead of describing the destination literally. Same name everywhere that destination appears: the page's own nav self-link, and the cross-link button on the other side.

## Résumé hero: Text Fall

The `/resume/` `<h1>` name is a canvas particle effect (`assets/js/text-fall.js`), ported from a React/canvas component the user supplied ("Text Fall"). Same accessibility pattern as spotlight-text: `.text-fall-plain` (the real "Bhavesh Nakum" text) is what's actually in the DOM and stays visible by default; the script adds `.text-fall-ready` to the heading only once it's confirmed set up, and only then does CSS swap to the canvas and visually clip the plain text off-screen (never `display:none`, so it's still the `h1`'s accessible name). No JS, a script error, or `prefers-reduced-motion` all just leave the plain heading showing.

- **It's a texture, not literal text.** Particles are sampled from an alpha mask of the rendered name (`buildTextMask`/`sampleTargets`), so their *positions* trace the name's shape — but each particle's glyph is a random monospace character (`randChar()`), re-rolled continuously via `maybeScramble`. No code path ever paints a particle with its "correct" letter. This matches the original component's aesthetic (a "digital noise" title, not a dot-matrix font) — the readable name lives in `.text-fall-plain`, the canvas is decorative.
- **Density is tuned via `glyphSize`.** The example config pasted by the user (`glyphSize: 15`) produced only ~31 particles for a 13-character name — visually a sparse scatter, unrecognizable as any shape. Dropped to `glyphSize: 7`, giving several hundred sample points against the same mask — a legible dot-matrix-style density without hitting the 4200-particle cap (`MAX_PARTICLES` in `text-fall.js`). If the name ever changes, re-check this: fewer/longer characters need a different `glyphSize` to stay legible.
- **Interaction:** click toggles idle particles into a "fall" (gravity + bounce), then "form" back into place; a second click "spreads" them out again. Cursor proximity applies a magnetic pull (`applyMagnetic`) while hovering. `autoFall: true` + an `IntersectionObserver` also triggers the fall once the heading scrolls into view (≥80% visible), so the very first page load isn't a static scatter forever.
- **Deliberate cut from the original component:** the entire SVG-logo fallback mode (`LOGO_SVG_DESKTOP`/`MOBILE`, `svgToImage`, the logo branch in `ensureMask`) was dropped — this site always passes real text (`text: "BHAVESH NAKUM"`), so that whole code path would never execute. Also dropped: TypeScript types, and Framer's `RenderTarget`/static-export handling (this is a plain script tag, not a React/Framer runtime).
- **A real automation-only false alarm worth remembering:** the canvas rendered completely blank (0 particles) the first time this was tested against a local server, tracing to `dispScale` computing near-zero. Root cause was the *testing tool's* browser tab reporting a 0×0 viewport (`.text-fall-root.offsetWidth === 0`) because the pane was backgrounded — not a bug in `resizeCanvas()`/`updateBounds()`. A real visitor's tab always has real dimensions from first paint. `text-fall.js` already has a `ResizeObserver` on the root element that would self-correct if this ever happened for real (e.g. a tab restored from background with genuinely stale layout).

## Homepage background: Globe

Beyond Horizon (below) is now DEPRECATED, superseded by `assets/js/globe.js` — a rotating dot-sphere, plain WebGL, per explicit request ("instade of horaizon add this glob animation"). The user supplied a detailed React/Three.js "Globe" reference (real continent shapes dot-mapped from a GeoJSON land dataset fetched at runtime, drag-to-rotate, marker support); asked directly whether to load Three.js for a faithful port or hand-roll something dependency-free, the user chose hand-rolled — consistent with every other effect on this page (glitter, text-fall, dissolve, Beyond Horizon are all zero-dependency canvas/shader code; the console easter egg literally advertises "no framework"). The first pass had no drag interaction, no marker support, and no real geography — a uniform dot sphere. Geography was the wrong thing to cut, correctly called out ("the globe which i shared had map of world but in you glob there is nothing"). Fixed by baking the same land data the reference fetches live into the file at build time instead: `curl`'d Natural Earth's 110m-resolution land GeoJSON once, ran a plain-Python ray-casting script (no shapely — a from-scratch even-odd point-in-polygon test) to rasterize it into a 3°×3° lat/lng bitmask (61×120 cells), hex-packed to a ~1.9KB string embedded directly in `globe.js` as `LAND_MASK_HEX`. The dot-generation loop now skips any candidate point that isn't on land. This keeps the "no runtime dependency" property intact (the fetch happened once, during development, not on every page load) while still showing an actual, recognizable world map — Africa, Europe, and the Antarctic ring (which really is a solid band at every longitude around ~-90° to -84° latitude — not a bug, that's what circling the South Pole looks like) are all visible as it rotates.
- **Drag-to-rotate, added on request** ("make it bit bigger and intractive, i should be able to rotaete from its center using mouse same like i have guven you in code"). Horizontal drag spins it (`angleY`), vertical drag tilts it (`tiltX`, clamped to ±90° so it can't flip past the poles) — same two-axis mechanic as the reference. On release, a decaying velocity keeps it moving before auto-rotate resumes, matching the reference's momentum feel, without porting its separate target/lerp smoothing layer on top — not needed at this scale. Built on Pointer Events, not mouse events, so touch-drag on mobile works too at no extra cost, even though only "using mouse" was asked. `.hero-globe`'s `pointer-events` flipped from `none` to its default (`auto`) and picked up `cursor: grab`/`:active { cursor: grabbing }`; `.hero`'s existing `overflow: hidden` clips hit-testing along with paint, so dragging only works where the dots are actually visible, not across the whole (partly off-screen on desktop) square container. `.scroll-cue` sits at a higher `z-index` than the globe, so it stays clickable where their boxes overlap — verified via `elementFromPoint`.
- **One marker dot, Bangalore** (`12.9716, 77.5946`) — where the site's owner actually is — in amber (`#f59e0b`, reused from `glitter.js`'s own palette, not a new color) so it stands out from the plain blue land dots. A second, one-point draw call each frame using the same shader/attribute setup as the main cloud, just its own color and a larger point size. Only visible where it happens to project into whatever part of the sphere is currently in view — the desktop "half cut" crop means it's genuinely hidden part of the time, same as any other dot would be at that position; this isn't a bug specific to the marker, just the nature of showing half a rotating sphere.
- **India still wasn't recognizable after the first density bump (`LAT_STEP: 5° → 3°`) — because the ceiling was the *mask*, not the dot count.** More dots sampled from the same 3°-resolution (110m dataset) land mask just made the same blocky, coastline-blurred shape denser, not more accurate — a 3° cell is ~330km on a side, wide enough to blur India's coastline into an undifferentiated blob merging with the rest of Asia. Fixed by regenerating the mask from the 50m dataset (the reference's own source, finer than the 110m one used initially) at 1.5° resolution — re-ran the same `curl` + ray-casting script, verified via ASCII art that India's actual triangular taper is now visible in the raw mask data before trusting it, *then* matched the dot-placement grid to the new 1.5° resolution and scaled point size down again (`w/75 → w/105`) to keep the now much denser cloud from blurring together. The lesson generalizes: "add more dots" only helps once the underlying data can support the detail — below that, it's polishing a blur.
- **`touch-action: none`** added to `.hero-globe` alongside the drag handlers — without it, a browser can still claim a click-drag as its own pan gesture before `pointermove` ever reaches `globe.js`, which is exactly the kind of thing that works fine for mobile's coarse touch-drag (where the browser's default gesture and the desired one are closer) but silently breaks a trackpad or precision-pointer drag on desktop.
- **"A bit bigger"**: desktop `min(50vw, 480px)` → `min(58vw, 560px)`; mobile `min(72vw, 320px)` → `min(80vw, 360px)`.

- **How it renders:** a static buffer of ~400 points on a unit sphere (latitude bands every 12°, longitude step scaled by `1/cos(lat)` so points don't crowd near the poles — the same formula the reference itself uses for its dot layout). The vertex shader applies a fixed tilt (23°, matching the reference's default `initialLatitude`) plus an animated Y-axis spin, then a simple perspective divide (`focal / (z + camDist)`) computed directly in the shader rather than a full projection-matrix pipeline — there's no camera to move, no raycasting, no scene graph, so a 4×4 matrix stack would be unused machinery for one rotating point cloud. Each point is drawn as a `gl.POINTS` sprite (`gl_PointSize` scaled by the same perspective factor, so near dots read bigger than far ones) colored in the site's blue accent (`#1d4ed8`, reused directly — not a new color), with alpha tied to depth (`0.15` on the far side, up to `1.0` on the near side) so the sphere reads as a rounded volume, not a flat disc of dots.
- **"Cut from center" on desktop, full circle on mobile — a CSS trick, not a shader one.** `.hero-globe` is a fixed-size square container positioned `left:50%; bottom:0; transform:translate(-50%, 50%)` — shifting it down by exactly *half its own height* (a `transform` percentage, which resolves against the element's own box, unlike a `bottom` percentage, which resolves against the containing block's height and would make the offset depend on `.hero`'s height instead of the globe's). That puts the container's vertical center exactly on `.hero`'s bottom edge; combined with `.hero`'s existing `overflow:hidden`, precisely the top half renders and the bottom half is clipped away — a planet's curve rising into frame, per "in desktop i want globe to be visible half only like cut from center." The mobile media query (`max-width:640px`) drops the transform entirely and repositions with a plain `bottom:6%`, so the whole circle sits inside the viewport instead — verified via `getBoundingClientRect`: the container's math checks out exactly (e.g. at one tested size, top:700/bottom:1100 against a hero bottom of 900 — 200 of 400px visible, running vertical center precisely at the clip line) and mobile shows a complete, unclipped circle.
- **Deprecated (not deleted): `.hero-glow`/`.hero-glow-canvas` and their markup in `index.md`.** `beyond-horizon.js` itself is untouched and re-enablable by restoring the markup and swapping the `<script>` tag back in `home.html`.

## Beyond Horizon (DEPRECATED — kept for history, see "Globe" above)

After several rounds of independently-added hero decorations (pastel blobs, a multi-hue glitter canvas, a blue galaxy button, italic spotlight text, a page-corner/orb hint), the user flagged the accumulated result as not blending together — a real UX problem, not a nitpick: each addition had picked its own colors in isolation instead of drawing from one shared palette. The fix was a WebGL ambient background (`assets/js/beyond-horizon.js`, ported from a React/WebGL "sunrise over a planet edge" component the user supplied) plus retinting everything else to match it, rather than adding yet another independently-colored layer. This went through two color directions before landing: a near-black night-sky version first, then back to white/light per explicit follow-up feedback — see "light-theme remap" below for how the same effect works on either.

- **What it is:** a full-bleed canvas (`.hero-glow`/`.hero-glow-canvas`, behind everything else in `.hero`) rendering a glowing horizon — a bright core sitting on the edge of a huge disc, with volumetric haze rising off it. Cursor movement subtly parallaxes the glow (eased, not snapped); hovering the hero saturates the core and widens the rim. Ported faithfully: the GLSL is written from scratch (the reference's own comments note its source engine's compiled shader carries a commercial license, so nothing from it is transcribed — only the *composition*, which is a description of what's visible, plus constants the original author measured off a reference capture, e.g. `HORIZON_Y = 0.7055` from the brightest measured pixel). React scaffolding (props/refs/useEffect) is dropped for one hardcoded `CONFIG` object and plain DOM APIs, matching every other canvas effect on this page — this runs exactly once, so a reusable component API would be unused abstraction.
- **The `fit` dial is what makes it responsive, not a media query.** Every measured constant is in units of the element's *width*, which is exactly right at the reference's aspect ratio and wrong at any other: hold the width and grow the height (a phone in portrait) and a naively-ported version keeps the glow's absolute size while the empty space around it grows, leaving a small dot lost in a big empty field — confirmed exactly this way in an early check before `fit` was wired in. `unit = (aspect / REF_ASPECT) ^ fit` rescales every position by that factor; `fit: 0.5` (shipped) is the geometric mean between width-locked (`0`) and height-locked (`1`), because the two demands genuinely pull opposite ways — glow *size* wants to track height, horizon *curvature* wants to track width (a planet edge crossing a narrow phone frame really is nearly straight, so the arc flattening out on mobile is correct, not a bug). Verified at 375×812, 768×1024, 1440×900, and standard desktop — the glow stays anchored behind the hero text at every width instead of drifting into empty space.
- **Colors are blue (`#1d4ed8`), not violet — and the hover state is deliberately tamer than the reference.** An earlier pass picked violet as the accent since nothing else on the page constrained the choice; explicit feedback ("our overall colour palette has blue but in landing page background you are putting like perpel") corrected that — the site's real identity is blue (Grind `#1d4ed8`, Chaos `#6ec1ff`), so `coreColor`/`--accent` now reuse `#1d4ed8` exactly rather than inventing a new hue. Separately, and more importantly: dark text sitting over the shader's saturated "core" color only has ~2.5:1 contrast *regardless of which hue that core is* — violet or blue, a fully-saturated core is always going to be too dark for `#14171c` text to read well against. The reference's hover state amplifies haze reach by roughly 8× (`hazeGain: 1.15 → 9.0`), and since the hover trigger is *any* mouse movement over the whole hero (not just over a button), that low-contrast zone was spreading up toward the headline on ordinary cursor movement — the exact bug reported ("text is not readable when purple light is increasing that effect"). Fixed on three fronts, all in `beyond-horizon.js`: `hazeGain`'s hover target cut to `3.0`, `rimGain`'s to `1.3`, and the final remap's core-color threshold tightened (`smoothstep(0.45, 1.0, lum)` → `smoothstep(0.62, 1.0, lum)`) so the poor-contrast core color stays confined near the horizon instead of reaching text height.
- **A second pass: the haze was still reaching the subhead at REST, not just on hover.** The hover-specific fix above wasn't enough — the *baseline* haze (`CONFIG.haze: 3`, `brightness: 2`) was still tall enough to visibly tint the bottom of "Poke around..." with zero interaction, confirmed by screenshot. Cut `haze` to `1.6` and `brightness` to `1.4` (both direct multipliers, so this scales the whole effect down globally, not just the hover delta), and moved `horizonY` from `0.7055` (the reference's measured value) — this is the one place this port deviates from a "measured, not guessed" constant on purpose: readability over fidelity. `horizonY` moved further still on a follow-up request to push the glow "closer to the bottom of the screen" — `0.7055 → 0.8 → 0.9`. Because `fit` (see above) already normalizes every position by aspect ratio, this one constant applies identically on mobile and desktop — no separate mobile tuning needed. Re-verified by hovering directly over the headline and subhead at each step — the background behind them stays white regardless of cursor position, both at rest and on hover.
- **Light-theme remap: why the shader needs two separate "backgrounds."** The reference's math is *additive* — it starts from a dark canvas and only ever adds brightness, so the glow reads as a light source purely because everything around it stays near zero. Point that same math at a white canvas and it breaks: `col` starts near-white already, so any addition clips straight to white almost everywhere and the glow vanishes (this happened, and looked like a wall of solid color, before the fix). The shader keeps a hardcoded `PHYS_BG` (near-black) as the physics-only baseline the light math actually runs against — untouched from the original dark version — and only at the very end remaps that computed brightness onto the *visible* palette: `lum = luminance(col); color = mix(mix(uBg, uMid, 0.05), mix(mix(uBg, uMid, smoothstep), uCore, smoothstep), above)`, where `uBg`/`uMid`/`uCore` are `CONFIG`'s white/light-blue/blue. Net effect: "no light" (originally near-black) → the visible white background; "light" (originally the bright core) → the saturated blue described above; the `above` term keeps a faint tint below the horizon line so the curve stays legible on white too, not just wherever the glow itself happens to be bright. This is a purely cosmetic remap — physics, motion, parallax, and the `fit` responsiveness above are all untouched, and changing the color story again (light, dark, or otherwise) would only mean changing `CONFIG`'s colors, not this logic.
- **This is the single color source for the whole homepage**, not just a background. `.theme-home`'s `--accent` (`#1d4ed8`) matches the shader's own `coreColor` exactly, so the background effect and the site's own established accent are one swatch, not an independently-invented one. The blob/glitter canvas's unrelated amber and green tones were the actual clashing colors that needed to go — removing them, not layering another independent palette on top, is what actually fixed "doesn't blend in," on both the violet and the blue pass.
- **`.hero-glitter` runs again, layered over `.hero-glow`.** Deprecated when Beyond Horizon first shipped, then explicitly asked back ("i want both effect in landing page"): `display:none` removed, `<script>` tag restored in `home.html`. The two coexist because `.hero-glitter`'s canvas background stays transparent between star draws (see `glitter.js`) while `.hero-glow`'s is opaque (`alpha:false`) — later in DOM order at the same `z-index:0`, glitter paints on top and only its star pixels are opaque, so the horizon glow shows through everywhere else. `brightness`/`starSize`/`particleCount` bumped up (0.55→1, 2.2→4, 70→160) per follow-up feedback that the colors weren't clearly visible against white — verified via `getImageData`: real configured colors (blue/orange/teal) were rendering correctly the whole time, just too sparse (~0.1% of pixels) to read as more than faint dust; doubled coverage to ~0.23%.
- **`.hero-blobs`, `.page-corner`/`.portal-orb`, and the dissolve "Thanos snap" transition stay DEPRECATED, not deleted.** The page-corner/orb hint and its click-triggered particle-dissolve (`assets/js/dissolve.js`) were removed per explicit feedback ("remove that page and thanos effect... it not what i am looking for") — the spotlight-text hint (desktop-only) is now the one path into `/life/` from the homepage itself, plus wherever a visitor lands on `/resume/` (see the galaxy-button entry below). All three are disabled via `display: none` rules in `home.css` (`.page-corner`/`.portal-orb` need `!important` since a later `@media (max-width: 640px)` rule would otherwise re-enable the orb on mobile), markup and JS files fully intact. `dissolve.js` isn't loaded by `home.html` anymore (its `<script>` tag is commented out, file untouched) — a script with no visible/clickable triggers left to attach to has nothing to do. Re-enabling any of these needs at most one CSS rule removed and one script tag restored.
- **`.hero-dim` → `.hero-hover-glow`, now DORMANT.** Originally a dark radial gradient dimming the page on galaxy-button hover; inverted into a bloom once the page went dark, since dimming an already-dark page did nothing. The galaxy button that triggered it has since moved to the `/resume/` nav (see "The homepage: mostly no buttons" below), so this effect's `:has()` selector never matches anymore — left in place, not deleted, in case a future hero CTA wants the same treatment.

## The homepage: mostly no buttons, plus one deliberate exception

`.offset-btn`/`.keycap-btn` (the shared cross-side components) never appear on the hero — the idea is a homepage people poke around in rather than one that funnels them through a corporate CTA, per explicit direction: "home page should be interactive and center of attraction... people should spend more time on home page to explore." An overt "Explore" CTA (`.galaxy-button`) lived here for a while as a deliberate exception, then moved to the `/resume/` nav entirely per explicit follow-up request — see below for where it lives now.

- **Backgrounds, in order of who's currently active:** `.hero-globe` (a rotating dot sphere) and `.hero-glitter` (canvas warp-tunnel) run together, layered — see "Homepage background: Globe" above for how. `.hero-glow` (Beyond Horizon, DEPRECATED), `.hero-stars` (CSS twinkling dots, DEPRECATED, superseded by `.hero-glitter` before glitter was itself briefly superseded and then brought back), and `.hero-blobs` (cursor-reactive pastel blobs via `hero.js`'s `--mx`/`--my`, DEPRECATED) stay off. All three deprecated layers are fully intact and re-enablable.
- **The page-corner/portal-orb hint and its "Thanos snap" particle-dissolve transition are DEPRECATED** (not deleted) per explicit user feedback — "remove that page and thanos effect... it not what i am looking for." Both were once the plan for a fuller "the page tears away, particles drift left" effect on the jump into `/life/`; that got built (`assets/js/dissolve.js`, a click-triggered canvas particle sweep) and then explicitly un-asked-for once seen in practice. The galaxy button (below) is now the one path into `/life/` from the homepage, plus the spotlight-text hint. See "Homepage background: Beyond Horizon" above for how these are disabled.
- **Galaxy button — now lives in the `/resume/` nav, not the homepage.** A structural port of a CodePen "galaxy button" the user supplied (HTML/CSS/JS, no framework attached), CSS in `professional.css`. Lived in `.hero-inner` as an overt "Explore" CTA for a while; moved to replace `.keycap-btn` as the "into `/life/`" nav link on `/resume/` per explicit request ("i want explore button to be moved to .../resume/ page and place it instade of The Chaos button"). Its label changed from "Explore" (a hero-CTA verb) back to "The Chaos" (a nav destination name, matching "The Grind" next to it) — a nav item names where it goes, a big hero button can afford a verb. Mechanics: a single `--active` custom property (0 at rest, 1 on hover/focus) that every child reads via `var()` — the dual radial-gradient background, the glow/inset box-shadow, the spark rim, and the star ring all wake up together. The star ring is genuinely 3D (`.galaxy__ring` tilted via `rotateX`/`rotateY` inside a `perspective`d parent), not a flat circle. The "spark" rim is a masked wrapper that flips between top/bottom half on a stepped timer, with a continuously-spinning conic-gradient pseudo-element underneath. Per-star orbit distance/size/alpha/duration/delay come from `assets/js/galaxy-button.js`. Two things changed for the nav context: sized down to match `.site-header .offset-btn`'s scale (`padding: 0.5rem 1.1rem; font-size: 0.9rem`) instead of the hero's much larger footprint, and the star orbit distance in `galaxy-button.js` scaled down from 30–90px to 14–38px to match (this is the component's only use site-wide now, so the shared script was tuned for its one caller rather than parameterized). `--hue` moved to 205 — the personal theme's own accent (`#6ec1ff`) — instead of whatever color the homepage background happened to be at the time, since this button always leads to `/life/` regardless of where it lives, the same convention `.keycap-btn` used. All animations drop out under `prefers-reduced-motion`, leaving a plain static pill. `.hero-hover-glow` (the homepage's hover-bloom effect keyed to `.galaxy-button:hover` inside `.hero`) is now dormant — left in place since it costs nothing when its selector never matches, not deleted.
- **The Grind still starts with a scroll**, but the "keep going" scroll-cue is now a real `<a href="/resume/">`, not just a hint — this had to change from the original plain-div version, because `prefers-reduced-motion` skips the entire scroll-driven mechanic below, and with no CTA button left on the page, reduced-motion/no-JS/keyboard users would otherwise have had zero path to `/resume/` from the homepage. Never rely on a single JS-only mechanic being the sole path to a page.
- **Spotlight text — desktop-only, hidden entirely on mobile.** `.spotlight-text` ("I left the interesting parts out of the résumé.", italic Fraunces) sits top-right, a recreation of the Cred "flashlight" effect — a dim base layer and a pixel-aligned bright duplicate on top, the bright one masked by a `radial-gradient` that follows the cursor (`--spot-x`/`--spot-y`, `mask-image`), so hovering sweeps a small circle of full brightness across the text. `hero.js` only dims the text and wires up the cursor tracking (adding `.spotlight-ready`) when `matchMedia('(hover: hover)')` actually matches, i.e. a real mouse — without JS or under reduced motion on desktop, it falls back to plain readable `var(--muted)`-colored text rather than disappearing, since there's no way to feature-detect "hover" without JS. On mobile (`max-width: 640px`) it's `display: none` outright, per explicit request — "hiddentxt should be hidded tottay and it should work on only desktop... in mobile i dont want that effect or feature." An earlier version instead showed the plain fallback text on mobile (following the "always leave a real link" pattern used elsewhere on this page); the user's instruction here explicitly overrides that for this one element. `--spot-size` (the reveal radius) is a `@property`-registered custom property so it can transition smoothly on hover/focus-visible; `--spot-x`/`--spot-y` update instantly via `pointermove`, no transition, so the spotlight tracks the cursor without lag. Now the one remaining hint at `/life/` on the homepage itself, since the page-corner/orb is deprecated and the galaxy button moved to the `/resume/` nav (see below).
  - **Genuinely invisible at rest, not just faint.** `.spotlight-dim`'s color was `rgba(20,23,28,0.08)` — a deliberately near-invisible 8% opacity, but not zero. Follow-up request: "make it complitly hidden only if cursor is on top of text than it should be visible." Changed to `color: transparent`. `.spotlight-bright` was already masked to nothing at rest (`--spot-size: 0px`), so between the two, nothing renders at all until the cursor's flashlight circle sweeps over the text — same reveal mechanism as before, just a fully-hidden starting point instead of a faint one.
  - **The two layers must share `font: inherit`, not just matching colors.** They're the same text rendered twice and have to line-break identically, or the mask reveals bright glyphs sitting somewhere the dim glyphs underneath aren't — this actually happened: an early version bolded only the bright layer, which widened its glyphs enough to wrap differently at some (but not all) viewport widths, so it looked fine on mobile and visibly double-exposed on desktop. Any future style tweak to one layer needs the identical tweak on the other, or use `font: inherit`/shared properties on the parent so both pick it up automatically.
- **A console-only easter egg, homepage only:** a styled `console.log` (`hero.js`) pointing curious devs at the GitHub source — visible via the browser's DevTools console (Cmd+Option+J in Chrome), not on the page itself. A Konami-code keyboard listener was tried and removed: it worked, but had zero real discovery rate without an on-page hint, and a hint defeats the point of a hidden code. Lesson: an easter egg needs *some* plausible discovery path (a known convention like "check the console," a visible hint, or both) — "technically present but unfindable" isn't a feature, it's just more code to maintain.

## Scroll-to-enter and page transitions (`v3-transition`, complete)

- **DEPRECATED — scroll-to-enter.** Used to auto-navigate to `/resume/` once an `IntersectionObserver` on a sentinel past a `.scroll-runway` spacer detected the user had scrolled to the bottom (`assets/js/hero.js`). Removed per explicit feedback: "user will not scroll they will just try to scroll down or press see more button" — real visitors don't commit to a long deliberate scroll, and the mechanic meant the footer (right after the sentinel in `home.html`) was never actually reachable, since navigation fired the instant the sentinel came into view. The scroll-cue "keep going" link — always a real `<a href="/resume/">` — is now the *only* path from the homepage into `/resume/` via scroll intent, for everyone, not just a reduced-motion fallback for the mechanic above. `.scroll-runway`/`#hero-sentinel` removed from `index.md`'s markup entirely (they'd otherwise just be a wasted blank gap working against "footer reachable on the same page"); `hero.js` returns early before ever setting up the observer, code left in place below the `return` for reference. Net effect: scrolling past the hero now reveals `.home-footer` directly, one screen-height down, same as any normal page.
- **DEPRECATED — the scroll-veil.** Built up anticipation via `--scroll-progress` as the user scrolled toward the (now-removed) sentinel; a `position: fixed` radial blue glow (`.scroll-veil`) used that as its `opacity`. `hero.js` no longer computes `--scroll-progress` at all, so this would stay permanently invisible even if re-added to the page; removed from `index.md`'s markup along with the runway/sentinel it was tied to. CSS rule and computation logic both left intact in their files.
- **The page transition itself is a wipe, not a cross-fade:** `@view-transition { navigation: auto; }` in `tokens.css` opts every page into the browser's native Cross-Document View Transitions API (pure CSS, no JS). `::view-transition-new(root)` animates in via `clip-path: inset()` (bottom-to-top reveal, echoing the scroll-down gesture) while `::view-transition-old(root)` just dims. This is what every navigation on the site gets by default, including arrival at `/life/`. Disabled under `prefers-reduced-motion`.
- **DEPRECATED — a canvas "Thanos snap" on the jump into `/life/`.** `assets/js/dissolve.js` intercepted clicks on `.page-corner`/`.portal-orb` specifically, added a `.dissolving` class that faded the hero to black, and drove a `<canvas>` of small (1–2.5px) squares blown apart to the left before calling `location.href`. Particles were sampled per real content element (`h1`, subhead, the galaxy button, spotlight-text, scroll-cue, the hint links themselves) rather than one uniform full-viewport grid, with each particle's delay a function of its own x-position so the dissolve visibly swept right-to-left. Built after being explicitly deferred earlier ("which we will do once landing page is done"), then explicitly un-asked-for once seen in practice ("remove that page and thanos effect... it not what i am looking for") — turns out the fuller version wasn't wanted after all once it existed. `/life/` now gets the same sitewide `@view-transition` wipe as every other page, no exception. File fully intact, just not loaded (see "Homepage background: Beyond Horizon" above).
